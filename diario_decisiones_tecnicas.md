# Diario de decisiones técnicas

El proyecto se desarrolló durante tres semanas. En la primera semana realicé los niveles básico, intermedio y avanzado. Las dos semanas siguientes las dediqué al desarrollo, evaluación y estabilización del proyecto de nivel experto.

| Semana / Nivel | Decisión tomada | Alternativas que consideré | Por qué elegí esta opción |
|---|---|---|---|
| Semana 1 / Nivel básico | Utilicé Groq como proveedor del modelo y guardé la clave en una variable de entorno cargada desde `.env`. También desarrollé una versión directa y otra con LangGraph. | Consideré utilizar Ollama en lugar de Groq, además de crear solamente una de las dos versiones del programa. | Elegí Groq porque ya lo había utilizado en proyectos anteriores y conocía su funcionamiento, mientras que Ollama era una herramienta completamente nueva para mí. Esto me permitió centrarme en los objetivos de la práctica y reducir la curva de aprendizaje. No obstante, en el futuro es muy probable que sustituya Groq por Ollama en este mismo proyecto para aprender a utilizar modelos locales y reducir la dependencia de servicios externos. |
| Semana 1 / Nivel intermedio | Añadí memoria conversacional, un mensaje de sistema y persistencia del historial en archivos JSON. | Guardar el historial en texto plano, conservar solamente el último mensaje o utilizar una base de datos. | Elegí JSON en lugar de texto plano porque me permitía guardar el historial de forma estructurada, conservando claramente el rol y el contenido de cada mensaje. Además, podía recuperar y procesar posteriormente la conversación sin interpretar manualmente el texto, y seguía siendo un formato sencillo para esta práctica. |
| Semana 1 / Nivel avanzado | Construí un agente que consulta PokeAPI mediante herramientas validadas, tanto manualmente como con LangGraph. | Permitir que el modelo respondiera con sus conocimientos, consultar cualquier URL o crear una única herramienta genérica. | Elegí utilizar herramientas porque me permitían obtener datos actuales y verificables. Decidí separar las consultas de Pokémon y objetos, validar sus argumentos y utilizar una lista cerrada de funciones para reducir errores y evitar que el modelo ejecutara llamadas inventadas. |
| Semana 2 / Nivel experto | Dividí el tutor en tres agentes: coordinador, tutor-investigador y evaluador, utilizando estado compartido y salidas estructuradas validadas con Pydantic. | Crear un único agente, permitir respuestas en texto libre o separar cada operación en un agente diferente. | Elegí esta separación porque así podía asignar una responsabilidad clara a cada agente y probarlos de manera independiente. Utilicé salidas estructuradas para no depender de interpretar texto libre y para detectar decisiones incoherentes antes de ejecutar herramientas. |
| Semana 2 / Nivel experto | Utilicé Tavily Search y Tavily Extract restringidos a documentación oficial de Python, Java y Git. Organicé el flujo como buscar, seleccionar, extraer y redactar. | Usar blogs, confiar en la memoria del modelo, crear scrapers propios o mantener una copia local de toda la documentación. | Elegí Tavily porque me permitía localizar y extraer información actualizada sin tener que desarrollar un scraper para cada documentación. También añadí validaciones de dominios, URL y citas para trabajar con fuentes fiables y evitar que el modelo inventara referencias. |
| Semana 3 / Nivel experto | Implementé una versión manual y otra con LangGraph, con revisión limitada, rúbricas privadas, guardado de progreso, logging seguro y pruebas automatizadas y reales. | Conservar solo la orquestación manual, delegar todo el flujo a LangGraph o comprobar únicamente las respuestas manualmente. | Decidí mantener las dos versiones porque quería compararlas y reutilizar los mismos agentes y herramientas. Establecí límites para evitar ciclos infinitos, utilicé rúbricas privadas para corregir ejercicios sin revelar la solución y añadí pruebas para comprobar el funcionamiento conjunto de todos los componentes. |
